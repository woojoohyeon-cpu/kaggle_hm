# 仮説駆動の全体設計メモ

コンペ: H&M Personalized Fashion Recommendations(MAP@12)。
本メモは「候補生成 → classificationによる再ランキング」という2段階アプローチを前提に、
仮説を数値で検証した結果と、そこから導いた特徴量・候補生成の設計方針をまとめたもの。

## 1. 全体アプローチ

- (customer, article)のペアを1行とし、対象週に購入されたら label=1、候補に入ったが未購入なら0とする**二値分類/ランキング問題**として定式化する。
- Stage 1: 候補生成(recall) — 自己リピート・人気度・共起・コンテンツ類似などを並列に用意しユニオンを取る。
- Stage 2: LightGBM(binary or LambdaRank, group=customer_id)で再スコアリングし上位12件を提出。
- 検証は時系列バックテスト必須(ランダムCV不可)。カットオフ日以前のデータのみで特徴量を計算しリークを防ぐ。

## 2. データの前提

- articles.csv: 105,543行(商品マスタ、色違い含むarticle単位)。同一product_codeの色違いが多数存在。
- customers.csv: 1,371,980行。FN/Activeはほぼ欠損で実質使えない。有効なのはage・club_member_status・fashion_news_frequency・postal_code程度。
- transactions_train.csv: 31,788,324行(2018-09-20〜2020-09-22)。price列は**スケーリング済み(0.000017〜0.591525)で実通貨単位は不明**。sales_channel_id: 1=店舗, 2=オンライン。

## 3. 仮説検証ログ(2026-07-25実施)

検証は全取引31,788,324件をduckdbで集計(customer_idを整数サロゲートキーに変換して高速化。詳細は8節)。

| # | 仮説 | 判定 | 数値根拠 |
|---|------|------|----------|
| H1 | 同じ商品/色違いを買う傾向がある | **採用** | 完全同一article再購入14.1%、同一product_codeの色違い9.1%、計23.2%がリピート系。残り76.8%は完全新規商品。→自己リピート候補は有効だが、それだけでは候補の大半をカバーできない前提で設計する |
| H2a | 男性服を繰り返し買った人は男性服を買い続ける | **採用(強い)** | Menswear購入3回以上の顧客(182,391人)は、全購入中のMenswear比率が平均26.8%(母集団シェア5.6%の4.8倍) |
| H2b | 子供服を買った人は継続して買う | **採用(強い)** | Baby/Children購入3回以上の顧客(121,607人)は同比率36.3%(母集団シェア3.8%の9.6倍) |
| H2c | 女性服を繰り返し買った人は女性服を買い続ける | **棄却(単独特徴量としては弱い)** | Ladieswear購入3回以上の顧客(923,705人)は同比率70.9%(母集団シェア64.2%の1.1倍)。母集団の大半が元々Ladieswearを買うため判別力が低い。index_group単位ではなくsection_name/product_type_nameなど粒度の細かいカテゴリで嗜好を捉える |
| H3 | 店舗ではアクセサリ・靴下など付随購入が起きやすい | **採用(効果は中程度)** | 衣類を含むバスケットに対する付随購入(Accessories/Socks & Tights/Underwear)併買率: 店舗23.0% vs オンライン18.6%(1.24倍)。方向性は支持されるが差はマイルド |
| H4 | 季節性・トレンドに大きく左右される(ファストファッション) | **採用(強い)** | 週次取引数に明確なスパイク: 2018-11-19(Black Friday週, 45.4万件)、2019-06-17〜24・2019-11-25・2020-06-15〜22 付近で急増。2020-03-16〜04-27は明確な落ち込み(COVID-19店舗休業の影響と推測)、6月にかけて回復。トレンド系特徴量は必須だが、COVID期は非定常なレジームシフトとして特別扱い(除外 or 別重み)が必要 |
| H5 | 自分の予算に合わせた価格帯で買う傾向がある | **採用** | 顧客ごとの価格CV(std/mean)平均0.525 < 母集団CV 0.689。個人内のばらつきが母集団より小さく、価格帯の存在を支持 |
| H6 | オンラインは送料無料の閾値まで買い足す | **棄却(直接検証不可)** | price列が実通貨単位不明のスケーリング値のため、「〇〇ドル以上」という絶対閾値は検証できない |
| H7 | 店舗の方が予算が少なく、オンラインの方が高額・多点数を買う | **採用** | 平均単価: 店舗0.0229 < オンライン0.0299(+30%)。平均バスケット合計額: 店舗0.0586 < オンライン0.1218(+108%)。平均点数: 店舗2.55点 < オンライン4.08点。H6の間接的な裏付けにもなる |

## 4. 採用した仮説から導く設計

### 候補生成(Stage 1)

- 自己リピート候補: 過去に購入したarticle_id、および同一product_codeの色違い(H1)
- セグメント別人気候補: 顧客ごとのindex_group内訳(特にMenswear/Baby/Childrenは強い判別力、H2a/H2b)、より細かくはsection_name/product_type_name単位の嗜好で絞り込む(H2c)
- チャネル考慮の共起候補: 店舗購入者には衣類+アクセサリ/靴下/下着のペア候補を厚めに(H3)
- 直近トレンド候補: 直近N週間の急上昇商品(H4)。COVID期(2020-03〜04)をトレンド計算から除外 or 減衰重みを検討
- 価格帯フィルタ: 顧客の過去平均単価から大きく外れる候補は減点、または候補自体を価格帯で絞る(H5, H7)
- 人気度ベース候補は「直近26週間以内に販売実績のあるarticle」に限定する死に筋フィルタを適用(商品ライフサイクル仮説)
- コールドスタート顧客(購入0〜1回、全体の10.3%)には人気度ベースのフォールバック候補を優先的に厚めに割り当てる(コールドスタート比率)

### 特徴量(Stage 2, 分類/ランキング)

- user系: 購入頻度・直近性・平均単価・価格CV・channel利用比率(店舗/オンライン)・index_group/section別購入シェア
- item系: 直近人気度トレンド(COVID期除外済み)・価格・カテゴリ階層・color/product_code・最終購入からの経過週数(死に筋フラグ)
- user-item交差系: 当該article/product_codeの過去購入有無・回数・最終購入からの経過日数・価格乖離・channel×product_group_nameの併買実績
- 時間系: day-of-month(給料日効果、22〜29日に+20〜25%の取引増)を週次トレンド(H4)に対する補助的な季節性特徴量として追加
- 「同一product_code再購入」の回数・頻度を特徴量化する際は、間隔14日以内の再購入(交換行動の可能性)を購入意欲の強い信号として単純加算しない。同日多点購入(72.1%、1バスケット内の色/型番違いまとめ買い)と別日短期再購入は区別して扱う

## 5. 棄却した仮説

- H2c(Ladieswear単体でのリピート仮説): 母集団の大半が既にLadieswear購入者のため判別力なし。単独特徴量としては不採用、細粒度カテゴリで代替。
- H6(送料無料閾値): price列が匿名化・スケーリングされており実通貨での閾値検証が不可能なため棄却。ただしH7の結果が間接的に整合するため、設計上は「オンラインは高単価・多点数」という形で反映済み。

## 7. 検証設計上の注意

- 時系列データのためランダムCV不可。直近1週間(または複数週のrolling)を疑似テスト期間としたバックテストが必須。
- 特徴量はカットオフ日以前のデータのみで計算しリークを防ぐ。
- 季節性が強いコンペのため、単一週のバックテストだけでは不安定。複数期間での検証が望ましい。
- COVID-19による2020年3〜4月の落ち込みは一時的な外部要因であり、将来予測には再現しないため、トレンド系特徴量の学習データから除外するか別扱いにすることを検討。

## 8. 検証環境メモ(再現用)

サンドボックス環境はメモリ制約(約3.8GB)があるため、素朴なpandas全件ロードやcustomer_id(64文字文字列)をそのままgroup byキーに使うとOOMする。以下の対処で31M行の集計が数秒〜十数秒で完了する。

```python
import duckdb
con = duckdb.connect()
con.execute("PRAGMA threads=4")

# customer_id(文字列)を整数サロゲートキーに変換してから結合・集計する
con.execute("""
CREATE TABLE cust_map AS
SELECT customer_id, (ROW_NUMBER() OVER () - 1)::INTEGER AS customer_idx
FROM read_csv_auto('01_input/customers.csv')
""")

con.execute("""
COPY (
  SELECT cm.customer_idx, t.t_dat,
         CAST(t.article_id AS BIGINT) AS article_id,
         t.price, t.sales_channel_id::TINYINT AS sales_channel_id,
         CAST(a.product_code AS INTEGER) AS product_code,
         a.product_group_name, a.index_group_name,
         c.age::SMALLINT AS age
  FROM read_csv_auto('01_input/transactions_train.csv') t
  JOIN cust_map cm ON cm.customer_id = t.customer_id
  LEFT JOIN read_csv_auto('01_input/articles.csv') a
    ON CAST(a.article_id AS BIGINT) = CAST(t.article_id AS BIGINT)
  LEFT JOIN read_csv_auto('01_input/customers.csv') c
    ON c.customer_id = t.customer_id
) TO '02_output/features/trans_lite.parquet' (FORMAT PARQUET)
""")
```

以降はこの`trans_lite.parquet`に対してduckdbでSQLを投げれば、GROUP BY / DISTINCTを含む集計も高速(整数キー化前は同じ処理でOOMして失敗した)。
Claude Code環境ではメモリに余裕があればこの変換は不要な場合もあるが、大容量CSVを扱う際の定石として残しておく。
